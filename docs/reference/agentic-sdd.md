# Agentic SDD

The `/speckit.*` slash commands drive the core Spec-Driven Development (SDD) process — an **agentic process** your coding agent runs step by step. For a guided, end-to-end run see the [Quick Start Guide](../quickstart.md); this page is the detailed reference for each command — including arguments, output, and how they interact. For the philosophy behind the process, see [What is SDD?](../concepts/sdd.md). For bug triage, see [Agentic Bug Fix](agentic-bugfix.md).

The commands are designed to run in order, but only `/speckit.specify` is strictly required before `/speckit.plan`. The clarify, checklist, and analyze commands are quality gates you add for anything with meaningful ambiguity.

For evaluating an idea before committing to a specification, see
[Agentic Idea Assessment](agentic-assessment.md). Assessment is optional and
independent of the SDD process.

> [!NOTE]
> Commands are written in `/speckit.*` form throughout this page. GitHub Copilot's default skills mode uses `/speckit-*`; some other agents use `$speckit-*` (e.g. Codex, ZCode) or `/skill:speckit-*` (e.g. Kimi). See [Command invocation](integrations.md#command-invocation).

```text
/speckit.constitution -> /speckit.specify -> /speckit.clarify -> /speckit.plan -> /speckit.checklist -> /speckit.tasks -> /speckit.analyze -> /speckit.implement -> /speckit.converge
```

## Command overview

After `specify init`, these commands are available in the selected integration.
Integrations that support optional skills mode can select it with
`--integration-options="--skills"`; some integrations, including Copilot, use
skills by default.

| Command | Agent skill | Purpose |
| --- | --- | --- |
| `/speckit.constitution` | `speckit-constitution` | Establish or update project principles |
| `/speckit.specify` | `speckit-specify` | Define requirements and user stories |
| `/speckit.plan` | `speckit-plan` | Create the technical implementation plan |
| `/speckit.tasks` | `speckit-tasks` | Break the plan into actionable tasks |
| `/speckit.implement` | `speckit-implement` | Execute the tasks |
| `/speckit.converge` | `speckit-converge` | Assess implementation against the artifacts and append remaining work |
| `/speckit.taskstoissues` | `speckit-taskstoissues` | **Deprecated core command**; use the `github` extension for GitHub issues |
| `/speckit.clarify` | `speckit-clarify` | Resolve ambiguity before planning (optional quality gate; formerly `/quizme`) |
| `/speckit.analyze` | `speckit-analyze` | Check artifact consistency after tasks and before implementation (optional quality gate) |
| `/speckit.checklist` | `speckit-checklist` | Generate requirements-quality checklists (optional quality gate) |
| `/speckit.todo` | `speckit-todo` | List unfinished features with their stage, blockers, and next step |
| `/speckit.roadmap` | `speckit-roadmap` | Split a large piece of work into a roadmap of sub-features |
| `/speckit.audit` | `speckit-audit` | Audit all current specs and the shared code for cross-feature conflicts and regressions (read-only) |

## `/speckit.constitution`

Creates or updates the project **constitution** — the guiding principles that every later phase is evaluated against — and keeps dependent templates in sync. Run it once up front and update it whenever your principles change. Pass the principles as arguments.

```text
/speckit.constitution This project follows a "Library-First" approach. All features must be implemented as standalone libraries first. We use TDD strictly. We prefer functional programming patterns.
```

For a more general starting point:

```text
/speckit.constitution Create principles focused on code quality, testing standards, user experience consistency, and performance requirements.
```

## `/speckit.specify`

Creates or updates the feature **specification** from a natural-language description. Focus on the **what** and **why** — the user-facing behavior and goals — not the tech stack, which belongs in `/speckit.plan`.

This workflow may also maintain `checklists/requirements.md`, the built-in spec-quality checklist that `/speckit.specify` creates and `/speckit.clarify` re-evaluates. That lifecycle is separate from custom checklists generated by `/speckit.checklist`.

```text
/speckit.specify Build an application that can help me organize my photos in separate photo albums. Albums are grouped by date and can be re-organized by dragging and dropping on the main page. Albums are never in other nested albums. Within each album, photos are previewed in a tile-like interface.
```

## `/speckit.clarify`

Asks up to five targeted questions about underspecified areas of the current spec and encodes your answers back into `spec.md`. Run it as many times as needed before planning, each time tackling a different area. Optionally pass a focus area as an argument.

```text
/speckit.clarify Focus on the task card behavior: status changes, comment limits, and who can be assigned.
```

Clarifying before planning keeps you from designing on top of ambiguity. If `/speckit.analyze` later surfaces requirement gaps, come back and run `/speckit.clarify` (or `/speckit.specify`) again.

When `checklists/requirements.md` exists, `/speckit.clarify` may update its evaluated state as part of tightening the spec. This exception applies only to the built-in requirements checklist, not to custom review checklists.

## `/speckit.plan`

Runs the planning process to generate design artifacts from the spec. This is where implementation detail belongs — provide your tech stack, architecture, and technical constraints as arguments.

```text
/speckit.plan Use .NET Aspire with Postgres. The frontend is Blazor Server with drag-and-drop boards and real-time updates. Expose REST APIs for projects, tasks, and notifications.
```

For the photo-album example above:

```text
/speckit.plan The application uses Vite with minimal number of libraries. Use vanilla HTML, CSS, and JavaScript as much as possible. Images are not uploaded anywhere and metadata is stored in a local SQLite database.
```

## `/speckit.checklist`

Generates a quality checklist for the feature — think of it as **"unit tests for your requirements."** Rather than testing code, it checks whether the spec itself is complete, clear, unambiguous, and consistent (for example: "Are the drag-and-drop rules defined for every column?", "Is behavior specified for a deleted assigned user?").

Custom checklists generated by this command are reviewer-owned requirements-quality review artifacts. An agent may help evaluate them when explicitly asked, but implementation must not silently self-approve them. In a custom checklist, `[x]` means the reviewer determined the requirements-quality criterion is satisfied; it does not mean implementation work is complete.

Run it with no arguments for a broad pass, or pass a focus area to target one aspect:

```text
/speckit.checklist
```

```text
/speckit.checklist Focus on the Kanban board interactions and comment permissions.
```

Review the generated checklist. If it surfaces gaps, loop back to `/speckit.clarify` or `/speckit.specify` to tighten the spec before breaking the work down, then mark each custom checklist item `[x]` only after the requirements-quality criterion has been reviewed and satisfied.

## `/speckit.tasks`

Generates an actionable, dependency-ordered `tasks.md` from the design artifacts. Tasks are organized into phases: **Setup**, **Foundational** (blocking prerequisites), then **one phase per user story** in priority order, and a final **Polish** phase for cross-cutting concerns. Tests are generated within a user story's phase when requested rather than as a separate phase, and tasks are marked for parallel execution where possible.

```text
/speckit.tasks
```

## `/speckit.analyze`

Performs a **read-only** cross-artifact consistency and quality analysis across `spec.md`, `plan.md`, and `tasks.md`, reporting conflicts, gaps, and ambiguities (for example a task with no matching requirement, or a plan choice that contradicts the spec). It never edits files — it produces a report and can optionally suggest remediations for you to approve.

```text
/speckit.analyze
```

Run it before implementing, while the artifacts can still be adjusted cheaply. If it surfaces issues, **return to the earlier step that owns them** and fix them at the source — `/speckit.specify` or `/speckit.clarify` for requirement problems, `/speckit.plan` for design problems, `/speckit.tasks` to regenerate the task list — then re-run `/speckit.analyze` until it comes back clean. You can also run `/speckit.analyze` again after implementation as an extra review.

## `/speckit.implement`

Executes the tasks in `tasks.md`, running each phase in dependency order and respecting parallel markers.

Before executing tasks, it reads checklist checkbox state as a gate. Checklist markers are read-only for this command: `/speckit.implement` counts checked and unchecked items and asks before proceeding when any are unchecked, but it must not change checklist markers. For custom checklists, checked items mean reviewer approval of requirements quality, not completed implementation work.

For a small feature, run it once to build everything:

```text
/speckit.implement
```

For a large feature, work in stages to avoid overwhelming the agent's context — scope each run with an argument, validate the result, then continue:

```text
/speckit.implement Implement only the Setup and Foundational phases: project scaffolding and the project/task data model with basic CRUD. Stop before the user-story features.
```

```text
/speckit.implement Now implement the Kanban board user story: drag-and-drop between columns.
```

Verify each stage works before moving to the next.

## `/speckit.converge`

Assesses the codebase against the feature's spec, plan, and tasks to confirm nothing was missed. It is **append-only**: it never edits or deletes code, and its only possible write is adding tasks to `tasks.md`. Run it only after `/speckit.implement` has run on the current `tasks.md`.

```text
/speckit.converge
```

It first prints a severity-graded findings summary, then resolves to one of two outcomes:

- **Converged** — no gaps found. `tasks.md` is left byte-for-byte unchanged and you'll see a clean result like `✅ Converged — the implementation satisfies the spec, plan, and tasks.` You're done; proceed to review or open a PR.
- **Tasks appended** — gaps found. Converge appends them as new tasks under a Convergence section in `tasks.md` and tells you how many. Run `/speckit.implement` again to complete them, then `/speckit.converge` once more. Each pass finds fewer items; repeat until it reports converged.

## `/speckit.todo`

Lists the unfinished features with one stage, their blockers, and the next command for each. It also recommends one feature. The command is read-only. It takes facts only from the feature files and the roadmap files, never from the conversation. It covers only the specs root of the current checkout. With external storage, that root is the shared workspace.

```text
/speckit.todo
```

The command runs [`specify feature list --json`](core.md#list-features) and renders the report from that output. Each feature gets exactly one stage:

| Stage | Rule | Next step |
| --- | --- | --- |
| Unreadable | `spec.md`, `plan.md`, `tasks.md`, or a checklist file cannot be read or is a symlink, or the folder or its `checklists/` folder cannot be listed | Fix the file or folder (no command) |
| No spec | A prefixed folder has no `spec.md` and no feature below it, and is not an epic folder (see [Roadmaps](#roadmaps)) | Add `spec.md` to the folder. Before you delete the folder, make sure that it holds no `roadmap.md` (no command) |
| Needs clarification | `spec.md` or `plan.md` has a clarification marker | `/speckit.clarify` |
| Done | `tasks.md` has tasks, and all are checked | — |
| In progress | Some tasks are checked, and some are open | `/speckit.implement` |
| Tasks ready | `tasks.md` exists, and no task is checked | `/speckit.implement` |
| Planned | `plan.md` exists | `/speckit.tasks` |
| Spec ready | Only `spec.md` exists | `/speckit.plan` |

The first matching rule wins, in this order: Unreadable, No spec, Needs clarification, Done, In progress, Tasks ready, Planned, Spec ready.

A feature is blocked when its stage is Unreadable, No spec, or Needs clarification. Two more blockers change the next step:

- Open items in `checklists/requirements.md` make the next step `/speckit.clarify`.
- A `tasks.md` with no task makes the next step `/speckit.tasks`.

When both apply, `/speckit.clarify` wins. Items in other checklist files are reviewer items. The report lists them, but they never block a feature or change its next step.

A clarification marker is the text `[NEEDS CLARIFICATION` in `spec.md` or `plan.md`. In `plan.md`, a line `**<field>**: NEEDS CLARIFICATION` is also a marker. Text in code blocks and code spans is not a marker. A task is a line such as `- [ ] T001 …`. `- [x]` and `- [X]` mark a checked task.

The recommendation is the first unfinished feature in this order:

1. Unblocked features, by stage In progress, Tasks ready, Planned, Spec ready (rule `finish-before-start`).
2. Blocked features with a next command (rule `resolve-blocker`).
3. Blocked features with no command, No spec before Unreadable (rule `resolve-blocker`).

Ties go to the workspace-relative path. When no feature is unfinished, the rule is `no-unfinished`, and the next step is `/speckit.specify`.

An open task keeps a feature unfinished. If you drop a task, delete its line from `tasks.md`.

### Roadmaps

A roadmap splits one epic into sub-features. It follows the [spec of specs](../concepts/spec-of-specs.md) convention. This part holds the rules that `/speckit.roadmap`, `/speckit.specify`, `/speckit.plan`, `/speckit.implement`, and `/speckit.todo` use.

A roadmap is the file `specs/<name>/roadmap.md`, where `<name>` is a direct child folder of the specs root that does not start with `.` and has no whitespace. The report does not check other files, such as a top-level `ROADMAP.md`. To start one, give `/speckit.roadmap` a description of the work. After a long discussion, a short input that names the work is enough, because the findings of the conversation are part of the description:

```text
/speckit.roadmap A billing portal: invoices, payment methods, and usage reports
```

The command first writes `specs/<name>/brief.md`. The brief holds the findings, the decisions with their rejected options, the owners, and the sources from the input and the conversation. The command then reads only the brief. It splits the work into `planned` entries, puts each finding in the scope boundary of one entry, and writes `specs/<name>/roadmap.md` from the `roadmap-template`. It names each finding that fits no entry in its report. It then runs `specify feature list --json` to check the file, and names the next `/speckit.specify` command for each ready entry. It creates no feature and changes no other file.

The command stops when `specs/<name>/roadmap.md` exists, when the folder exists with no brief and no roadmap, or when the work is only one sub-feature. When the folder has `brief.md` and no `roadmap.md`, the command reads that brief and does not write it again. To fix a roadmap that missed findings, add them to the brief, delete `roadmap.md`, and run the command again.

The roadmap has one `## Context` section after the table. It holds the problem, the reason for doing the work now, `### Decisions`, and `### Sources`. Each decision has a title, the rejected options with a reason each, and a source as a PR number or a file path, in this form:

```markdown
- **Keep Valkey** (PR #4): keep the shared store. Rejected: Postgres, because the rewrite takes 3–5 days and gives no speed gain.
```

A decision number is never the only name of a decision, because projects renumber decisions.

To write a roadmap by hand, copy the template path that `specify preset resolve roadmap-template` prints to `specs/<name>/roadmap.md`. Then add one row for each sub-feature, and fill `## Context`.

A numbered roadmap folder `<name>` that has a regular `roadmap.md` and none of `spec.md`, `plan.md`, `tasks.md`, or `checklists/` is an epic folder. A `brief.md` does not change this. A numbered folder whose name has whitespace is never an epic folder. The feature report skips an epic folder as a feature and checks the folders below it. A numbered folder with a roadmap, any of those files, and no feature below it stays a feature row, so its open tasks still show. A folder with a feature below it is a container and is never a feature row. The report ignores its own `plan.md`, `tasks.md`, and checklists, but still checks its `roadmap.md`.

The roadmap has a Markdown table with the columns ID, Sub-feature, Intent, Scope boundary, Depends on, Status, and Sub-spec, and the optional column Waits on. The column order is free, and extra columns are allowed. Readers trim each cell and remove every `*` and backtick at both ends. An ID starts with a letter or a digit, then uses letters, digits, `-`, `_`, or `.` between parts, for example `R2.1`. Status is `planned`, `in-progress`, or `done`. In Depends on, Waits on, and Sub-spec, `—`, `–`, `-`, or an empty cell means "none". Depends on is a comma-separated list of IDs from the same roadmap. Waits on is free text that names an external change, person, or team, for example `PR #15 (alice)`. A roadmap with no Waits on column is valid, and its entries wait on nothing. Sub-spec is the feature directory, for example `specs/012-billing-payment-methods`. Trailing `/` characters on Sub-spec are allowed.

To start a sub-feature, give `/speckit.specify` the roadmap path and the entry ID. The command writes this back-reference as the **Input** line of `spec.md`:

```markdown
**Input**: Parent roadmap: `specs/<epic>/roadmap.md` → entry **R3**. <description>
```

Readers also accept the back-reference without `**Input**:`, bold, or backticks, and with `->` in place of `→`. The first matching line outside fenced code blocks wins.

When the roadmap has `## Context`, `/speckit.specify` copies it into the spec as a `## Roadmap Context` section directly before `## User Scenarios & Testing`, with a first line that names the roadmap. The section in the roadmap starts at the first `## Context` line outside fenced code blocks and ends before the next `#` or `##` heading outside fenced code blocks. When the entry has a Waits on value, `/speckit.specify` warns and names it, and still writes the spec.

Two commands write roadmap cells:

| Command | Cells | When |
| --- | --- | --- |
| `/speckit.specify` | Sub-spec = the new feature directory, Status = `in-progress` | After it writes `spec.md` for the entry |
| `/speckit.implement` | Status = `done` | When the row's Sub-spec names this feature and the feature meets the Done stage rule |

Each command changes only these cells in the row of its own entry. It does not change other lines, `## Context`, or `brief.md`. `/speckit.plan` and `/speckit.implement` also read the parent entry and the roadmap's `## Context`. They follow each decision and do not reopen a rejected option. A roadmap with no `## Context` gives no warning.

`specify feature list` reads every roadmap and computes these values for each entry:

- **Expected status**: `planned` when Sub-spec is "none", `done` when the sub-spec feature has the stage Done, and `in-progress` otherwise.
- **Ready**: the expected status is `planned`, no finding names the entry, each dependency is in the same roadmap with the expected status `done`, and Waits on is "none".
- **Roadmap recommendation**: the first ready entry, by roadmap path and then by row order. The next step is `/speckit.specify`. When no entry is ready, there is no roadmap recommendation.

An unknown dependency gives no finding, and the entry is never ready. A dependency cycle also gives no finding, and an entry in the cycle is never ready.

The report gives these findings:

| Kind | Cause |
| --- | --- |
| `unreadable-roadmap` | `roadmap.md` is a symlink, is not a regular file, cannot be read, is not UTF-8, or sits in a folder that the report can list but cannot search. The table has no header, no separator row, a row with a different cell count, an empty or invalid ID, or a duplicate ID. The report lists no entries for this roadmap. |
| `broken-link` | A back-reference or Sub-spec path is not valid. A Sub-spec is not a known feature. The back-reference of the sub-spec does not name this roadmap and entry. A spec names an entry whose Sub-spec is a different feature or that has no sub-spec. |
| `missing-entry` | A back-reference names a roadmap that does not exist or that the report cannot see (its folder cannot be listed or is a symlink), or an entry that the roadmap does not have. |
| `status-drift` | The stored Status differs from the expected status. A value other than the three statuses always differs. The report skips this check only when the entry row itself has a `broken-link` finding. A `broken-link` finding on another spec that names the entry does not skip it. |

A valid back-reference path has the form `specs/<name>/roadmap.md`. A valid Sub-spec starts with `specs/`, is relative, and has no `..` or empty segment. The report never reads a file at a path from a cell.

With local storage, parallel worktrees can change neighboring rows of the same roadmap. The merge then can give a conflict. Resolve the conflict by hand, then run `/speckit.todo` to check the roadmap.

## `/speckit.audit`

Audits the whole repository for the places where features meet. It checks that the current specs agree with each other and that the code at a shared subject still meets the current requirements of every feature that names it. `/speckit.analyze` and `/speckit.converge` check one feature. The audit does not check a requirement that belongs to one feature only. The report counts such requirements as "left to converge".

```text
/speckit.audit
/speckit.audit 003 007
/speckit.audit roadmap table
/speckit.audit save the report to reports/audit.md
```

With no input, the command audits every feature that [`specify feature list --json`](core.md#list-features) lists. With feature numbers, feature paths, or subject words, it audits that scope against every current feature that shares a subject with it, and it lists the features that it skipped.

The command is read-only. It runs the feature report, reads files, and runs read-only git commands. It never fetches, checks out, or stashes, and it runs no hooks. It runs tests only when the input names the test command. It writes a file only when the input asks to save the report. The path must be inside the code repository or the specs root, and the command does not overwrite a file unless the input says "overwrite".

Each feature gets a checkout state:

| State | Meaning | Effect |
| --- | --- | --- |
| `here` | The work of the feature is in this checkout | Its requirements are checked against the code |
| `elsewhere` | The work is only on a branch that this checkout does not contain | Its conflicts with `here` features are listed as merge risks. They never change the answer |
| `unknown` | No source gives evidence | It is never evidence for a finding, and it blocks a `yes` when it shares a subject with a `here` feature |

With local storage, every feature is `here`. With external storage, the specs of all branches are in one specs root. The command then decides each state from these sources, in order: git (the branch is merged, or a commit in `HEAD` names the feature folder), the files that the plan says the feature creates, and the `**Feature Branch**` field of the spec.

A requirement is historical only when a `here` feature, the constitution, or a guide that the constitution names states that it is replaced. A higher feature number is never proof. Two current requirements that conflict with no such statement give an `authority-unclear` finding, not a regression.

Each finding has a kind, a status (`verified`, `suspected`, `ambiguous`, or `unverifiable`), a severity from `CRITICAL` to `LOW`, the requirements with their feature folders, the code locations, the quoted evidence, and a fix. A `verified` finding quotes every requirement, and a code finding also gives `path:line`. The report starts with the answer:

- `yes`: every shared subject was checked, and no finding of `MEDIUM` or higher remains.
- `no`: at least one `verified` finding of `MEDIUM` or higher.
- `not determined`: a part was not checked, a `suspected` finding remains, or an `unknown` feature shares a subject with a `here` feature.

The report ends with a coverage table of what the command checked and what it did not check, with a reason. In a large repository, the command checks groups of features that share subjects, and it can give each group to a subagent.

## `/speckit.taskstoissues` (deprecated core command)

The core command is deprecated and will be removed in a future minor release.
It warns when invoked, then continues its existing workflow without installing
or enabling the extension automatically.

The recommended extension command optionally converts an existing `tasks.md`
into actionable GitHub issues. Install the extension from your project root:

```bash
specify extension add github
```

Then invoke it in your agent after generating tasks when you want to track
execution in GitHub:

```text
/speckit.github.taskstoissues
```

This command requires a GitHub `origin` remote and access to the GitHub MCP tools
for listing and creating issues. It creates issues only in the repository
identified by that remote and checks existing task IDs to avoid duplicates.
It is not required to implement tasks or converge on a feature.

> [!NOTE]
> GitHub issue tracking uses the bundled, opt-in [`github` extension](https://github.com/github/spec-kit/blob/main/extensions/github/README.md). Its recommended command is `/speckit.github.taskstoissues` (slash-hyphen integrations: `/speckit-github-taskstoissues`; Codex, ZCode, and Command Code skills: `$speckit-github-taskstoissues`; Kimi: `/skill:speckit-github-taskstoissues`); the deprecated core `/speckit.taskstoissues` remains available during migration. The `generic` integration registers the extension under its configured command directory in commands or skills mode. See the [installation and migration notes](https://github.com/github/spec-kit/blob/main/extensions/github/README.md#installation) for all integration-specific invocation syntaxes.
